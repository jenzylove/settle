A real example

"Let customers pay in their own currency (USD, EUR, JPY and IDR), and keep the top customers ranking correct."

Before anyone estimated this, Bob picked the 3 assumptions most likely to blow up the estimate, wrote a small experiment for each, and Settle ran every experiment against the real code.

blocked

The database money column uses a data type that can only hold numbers up to about 2 billion. A single large order in Indonesian rupiah (e.g. Rp 15,000,000 stored as 1,500,000,000 units) nearly maxes it out, and the running total across several orders will silently wrap around to a wrong number, breaking the leaderboard.

A single IDR order of 15,000,000 IDR stored as minor units (1,500,000,000) is already close to the 32-bit limit; any customer with multiple large IDR orders causes a silent integer overflow in the SUM, corrupting the ranking. Fixing it requires a schema migration to `bigint`, changes to the TypeScript type, the API response type, and any downstream consumer that reads `revenue_cents`.

✖ sum(amount_cents)::int overflows when IDR orders exceed INT_MAX (5448.3609ms)
blocked

Right now each order record stores only an amount number, with no label for which currency it is. To support four currencies the database needs a new 'currency' field on every order. That field does not exist today, so every order ever placed would need to be labelled retroactively and every piece of code that writes or reads orders must be updated.

Without a currency column there is no way to know whether a stored amount is USD cents, EUR cents, JPY yen, or IDR rupiah. Every existing row becomes ambiguous. Adding the column requires a schema migration on a live table, a backfill strategy for the 200k existing rows, updates to `createOrder`, the POST `/orders` handler, input validation, and all tests — before any FX logic can even start.

  ✖ orders table has a currency column (5432.2573ms)
blocked

The leaderboard is built by adding up order amounts. If those amounts are in different currencies — dollars, euros, yen, rupiah — you cannot just add them together; 10,000 yen is not the same as 10,000 dollars. Today there is no currency-conversion logic anywhere in the code, so the leaderboard would rank customers by a meaningless mixed-currency total the moment the first non-USD order is saved.

The current query does `SUM(o.amount_cents)` with no currency conversion. If a customer has one USD order (10,000 cents = $100) and one JPY order (10,000 yen = ~$67), the query adds 10,000 + 10,000 = 20,000 and treats it as $200 — ranking them above a customer with a genuine $150 order. Correct ranking requires an FX rates table, a conversion step in the query or application layer, and a strategy for stale rates — none of which exist in the codebase today.

✖ topCustomers ranks correctly when orders have mixed currencies (2383.5933ms)

How you use it

One sentence in, evidence out. On your code, on your machine.

Write the featureOne sentence in prove.yml, like "let customers pay in their own currency". Or describe it to the Settle mode in Bob IDE.
Bob finds the risksBob reads your code and names the assumptions the feature silently depends on, the ones that cost days if they are wrong.
Bob runs experimentsOne Bob per assumption, all at once, each in its own copy of your repo, writes the smallest test that proves or disproves it.
Settle checks the workSettle reruns every experiment itself instead of trusting Bob's word, then Bob writes the plan from what was actually found.

Why not just ask an AI

An AI can guess what might go wrong. Settle shows you, with a failing test.

A guess"Mixed currencies might affect your ranking." Maybe. How much? Nobody knows until someone builds it.
EvidenceA real test against your real code, the exact error or wrong number it produced, and the branch you can open.
A checked resultBob builds the experiments; Settle reruns them. An experiment that edits existing code or tests is not trusted.

Run it

On your repo, with your Bob.

cd your-app                   # a git repo
echo 'request: Add team accounts' > prove.yml
export BOB_API_KEY=...        # IBM Bob Shell, Inference scope
settle prove                  # risks, experiments, evidence, plan

Settle runs next to your code. Nothing is merged; every experiment stays on its own branch.

01 Blocked

The amount_cents column and the sum::int cast in the ranking query can hold IDR-sized amounts without…

The database money column uses a data type that can only hold numbers up to about 2 billion. A single large order in Indonesian rupiah (e.g. Rp 15,000,000 stored as 1,500,000,000 units) nearly maxes it out, and the running total across several orders will silently wrap around to a wrong number, breaking the leaderboard.

The `amount_cents` column (PostgreSQL `integer`, 32-bit, max 2,147,483,647) and the `sum(o.amount_cents)::int` cast in the ranking query can hold IDR-sized amounts without overflowing.

Why it matters. A single IDR order of 15,000,000 IDR stored as minor units (1,500,000,000) is already close to the 32-bit limit; any customer with multiple large IDR orders causes a silent integer overflow in the SUM, corrupting the ranking. Fixing it requires a schema migration to `bigint`, changes to the TypeScript type, the API response type, and any downstream consumer that reads `revenue_cents`.

A landmine. The experiment failed against today's code; this needs work before the feature.

The experiment Bob wrote · settle-experiments/integer-overflow-idr.test.ts
/**
 * Experiment: integer-overflow-idr
 *
 * Assumption under test:
 *   The `amount_cents` column (PostgreSQL `integer`, 32-bit) and the
 *   `sum(o.amount_cents)::int` cast in topCustomers() can hold IDR-sized
 *   amounts without overflowing.
 *
 * How it works:
 *   1. Confirms the column DDL is `integer` (not `bigint`).
 *   2. Inserts enough large IDR orders (1,500,000,000 cents each, representing
 *      15,000,000 IDR) for one customer so the SUM exceeds 2,147,483,647.
 *   3. Calls the real topCustomers() function and checks whether the returned
 *      revenue_cents for that customer is a positive number greater than the
 *      individual order amount — i.e., the sum is correct.
 *
 * PASSES  → assumption holds (no overflow detected)
 * FAILS   → assumption is broken (overflow detected, wrong value shown as evidence)
 */

import { test } from "node:test";
import assert from "node:assert/strict";
import { openDb } from "../src/db.ts";
import { topCustomers, createOrder } from "../src/server.ts";

// One IDR order of 15,000,000 IDR stored as minor units (sen/subunit × 100)
const IDR_ORDER_CENTS = 1_500_000_000; // 1.5 billion — near the 32-bit ceiling

// Two such orders sum to 3,000,000,000 which exceeds INT_MAX (2,147,483,647)
const ORDER_COUNT = 2;
const EXPECTED_TOTAL = IDR_ORDER_CENTS * ORDER_COUNT; // 3_000_000_000

test("column DDL is integer (32-bit), confirming the assumption is worth testing", async () => {
  const db = await openDb();
  try {
    const { rows } = await db.query<{ data_type: string }>(
      `SELECT data_type
       FROM information_schema.columns
       WHERE table_name = 'orders'
         AND column_name = 'amount_cents'`,
    );
    assert.ok(rows.length === 1, "column amount_cents not found in information_schema");
    // This is informational: we expect 'integer'. If someone already migrated to
    // bigint this assertion would fail and the experiment becomes moot.
    assert.equal(
      rows[0].data_type,
      "integer",
      `Expected column to be 'integer' (32-bit) but got '${rows[0].data_type}'. ` +
        "If this is 'bigint' the migration already happened and this experiment is moot.",
    );
  } finally {
    await db.close();
  }
});

test("sum(amount_cents)::int overflows when IDR orders exceed INT_MAX", async () => {
  const db = await openDb();
  try {
    // Use customer_id = 1 (guaranteed to exist after openDb seed)
    const CUSTOMER_ID = 1;

    // Insert ORDER_COUNT large IDR orders for this customer so the SUM overflows
    for (let i = 0; i < ORDER_COUNT; i++) {
      await createOrder(db, CUSTOMER_ID, IDR_ORDER_CENTS);
    }

    // Call the real ranking query — this is the code path under test
    const ranking = await topCustomers(db, 100);

    // Find the customer we just loaded with IDR orders
    const row = ranking.find((r) => r.customer_id === CUSTOMER_ID);

    assert.ok(
      row !== undefined,
      `Customer ${CUSTOMER_ID} not found in top-customers ranking after inserting IDR orders`,
    );

    // The correct total should be EXPECTED_TOTAL (3,000,000,000).
    // With a 32-bit overflow the value wraps or postgres throws an error.
    // Either way, we assert the returned value equals the mathematically correct total.
    assert.equal(
      row.revenue_cents,
      EXPECTED_TOTAL,
      `Integer overflow detected in revenue_cents! ` +
        `Inserted ${ORDER_COUNT} orders of ${IDR_ORDER_CENTS} cents each. ` +
        `Expected sum = ${EXPECTED_TOTAL} but got ${row.revenue_cents}. ` +
        `The ::int cast in sum(o.amount_cents)::int wraps/corrupts at 2,147,483,647.`,
    );
  } finally {
    await db.close();
  }
});

02 Blocked

The orders table already has a currency column so each row knows which currency its amount_cents is…

Right now each order record stores only an amount number, with no label for which currency it is. To support four currencies the database needs a new 'currency' field on every order. That field does not exist today, so every order ever placed would need to be labelled retroactively and every piece of code that writes or reads orders must be updated.

The `orders` table already has a `currency` column (or equivalent) so each row knows which currency its `amount_cents` is denominated in.

Why it matters. Without a currency column there is no way to know whether a stored amount is USD cents, EUR cents, JPY yen, or IDR rupiah. Every existing row becomes ambiguous. Adding the column requires a schema migration on a live table, a backfill strategy for the 200k existing rows, updates to `createOrder`, the POST `/orders` handler, input validation, and all tests — before any FX logic can even start.

A landmine. The experiment failed against today's code; this needs work before the feature.

03 Blocked

The top-customers ranking query produces a correct result when orders contain mixed currencies, because it…

The leaderboard is built by adding up order amounts. If those amounts are in different currencies — dollars, euros, yen, rupiah — you cannot just add them together; 10,000 yen is not the same as 10,000 dollars. Today there is no currency-conversion logic anywhere in the code, so the leaderboard would rank customers by a meaningless mixed-currency total the moment the first non-USD order is saved.

The top-customers ranking query (`topCustomers`) produces a correct result when orders contain mixed currencies, because it normalises amounts to a common unit before summing.

Why it matters. The current query does `SUM(o.amount_cents)` with no currency conversion. If a customer has one USD order (10,000 cents = $100) and one JPY order (10,000 yen = ~$67), the query adds 10,000 + 10,000 = 20,000 and treats it as $200 — ranking them above a customer with a genuine $150 order. Correct ranking requires an FX rates table, a conversion step in the query or application layer, and a strategy for stale rates — none of which exist in the codebase today.

A landmine. The experiment failed against today's code; this needs work before the feature.

/**
 * Experiment: does topCustomers normalise mixed currencies before summing?
 *
 * Assumption under test:
 *   The ranking query produces a correct result when orders contain mixed
 *   currencies, because it normalises amounts to a common unit before summing.
 *
 * Strategy:
 *   Create two customers in a fresh PGlite instance:
 *     - Alice: one USD order of 10 000 cents ($100) + one JPY order of 10 000
 *       yen (~$67).  Raw sum = 20 000.
 *     - Bob:   one USD order of 15 000 cents ($150).  Raw sum = 15 000.
 *
 *   If the query normalises correctly Bob should rank first ($150 > ~$167 is
 *   actually Alice still higher — let's tighten the numbers so the bug is
 *   unambiguous):
 *
 *     - Alice: USD 10 000 cents ($100) + JPY 6 700 yen (~$45).
 *       True USD value ≈ $145. Raw sum = 16 700.
 *     - Bob:   USD 15 000 cents ($150).  Raw sum = 15 000.
 *
 *   Correct ranking:  Bob ($150) > Alice (~$145).
 *   Buggy raw ranking: Alice (16 700) > Bob (15 000).
 *
 *   The test asserts that Bob is ranked first.  If the assumption holds
 *   (conversion logic exists) the assertion passes.  If the raw sum is used
 *   (today's code) Alice will appear first and the test FAILS, showing the
 *   wrong value.
 *
 *   No application code is modified.  The real topCustomers() function from
 *   server.ts is called directly against a real PGlite database.
 */

import { test } from "node:test";
import assert from "node:assert/strict";
import { PGlite } from "@electric-sql/pglite";
import { topCustomers } from "../src/server.ts";

test("topCustomers ranks correctly when orders have mixed currencies", async () => {
  // ── build a minimal in-memory DB ──────────────────────────────────────────
  const db = new PGlite();
  await db.exec(`
    CREATE TABLE customers (
      id     integer PRIMARY KEY,
      name   text NOT NULL,
      region text NOT NULL
    );

    CREATE TABLE orders (
      id           serial PRIMARY KEY,
      customer_id  integer NOT NULL REFERENCES customers(id),
      amount_cents integer NOT NULL,
      status       text NOT NULL,
      created_at   timestamptz NOT NULL
    );

    INSERT INTO customers VALUES
      (1, 'Alice', 'north'),
      (2, 'Bob',   'north');
  `);

  // Alice: one USD order ($100 = 10 000 cents) + one JPY order (6 700 yen).
  //   True value in USD ≈ $100 + $45 = $145.
  //   Raw sum of amount_cents = 10 000 + 6 700 = 16 700.
  await db.exec(`
    INSERT INTO orders (customer_id, amount_cents, status, created_at) VALUES
      (1, 10000, 'paid', now()),   -- USD $100
      (1,  6700, 'paid', now());   -- JPY ¥6700 ≈ $45
  `);

  // Bob: one USD order ($150 = 15 000 cents).
  //   True value = $150.  Raw sum = 15 000.
  await db.exec(`
    INSERT INTO orders (customer_id, amount_cents, status, created_at) VALUES
      (2, 15000, 'paid', now());   -- USD $150
  `);

  // ── call the real query ───────────────────────────────────────────────────
  const rows = await topCustomers(db, 10);

  await db.close();

  // ── assert correct ranking ────────────────────────────────────────────────
  // Bob's true USD value ($150) > Alice's true USD value (~$145), so Bob
  // must appear first if the query converts currencies correctly.
  //
  // If the query just sums amount_cents without conversion:
  //   Alice raw = 16 700, Bob raw = 15 000 → Alice ranked first → WRONG.
  //
  // The assertion will FAIL with today's code, showing Alice (revenue_cents=16700)
  // at position 0 instead of Bob (revenue_cents=15000).

  const first = rows[0];
  const second = rows[1];

  assert.equal(
    rows.length,
    2,
    `Expected 2 rows, got ${rows.length}: ${JSON.stringify(rows)}`,
  );

  assert.equal(
    first.customer_id,
    2,
    `Expected Bob (id=2, true USD $150) to rank first, but got ` +
      `customer_id=${first.customer_id} (${first.name}) with ` +
      `revenue_cents=${first.revenue_cents}. ` +
      `Second place: customer_id=${second.customer_id} (${second.name}) ` +
      `revenue_cents=${second.revenue_cents}. ` +
      `The query sums amount_cents without currency conversion: ` +
      `Alice raw=16700 (USD10000+JPY6700) was ranked above Bob raw=15000 (USD15000), ` +
      `which is incorrect — Bob's $150 is worth more than Alice's ~$145.`,
  );
});

The plan Bob wrote from the evidence.

Multi-currency feature — implementation plan

What we now know

  • INTEGER overflow is real (BLOCKED). The amount_cents column and the ::int cast in the ranking query cannot hold IDR-sized amounts; they will silently corrupt data at scale.
  • No currency column exists (BLOCKED). The orders table has no way to record which currency an order is in, so the data model cannot support multi-currency at all today.
  • Ranking is wrong with mixed currencies (BLOCKED). Because there is no normalisation step, summing USD cents alongside IDR cents produces a meaningless number; the top-customers query is incorrect by design the moment a second currency appears.

---

Landmines to fix first

  1. Change the column type from integer to bigint (demo/orders-api/src/db.ts, demo/orders-api/src/server.ts).

The amount_cents column definition and the sum(o.amount_cents)::int cast must both become bigint. A single IDR order can easily be 1 000 000 × an equivalent USD order; INT_MAX (~2.1 B) is reached with a handful of large IDR transactions. The TypeScript interface TopCustomer.revenue_cents must change to number (JS handles up to 2^53 safely).

  1. Add a currency column to orders (demo/orders-api/src/db.ts, demo/orders-api/src/server.ts).

Without knowing the currency of each row, normalisation is impossible. The column should be text NOT NULL with a check constraint (USD, EUR, JPY, IDR). The seed data, createOrder, and the POST /orders endpoint all need updating.

  1. Normalise to a common unit before summing in topCustomers (demo/orders-api/src/server.ts).

The ranking query must convert each row's amount_cents to a single reference currency (e.g. USD micro-units) using a static exchange-rate table before aggregating. Without this the ranking is undefined once orders span currencies.

---

Plan

  1. Migrate amount_cents to bigint; update cast, TypeScript type, and POST validation.
  2. Add currency column to schema; update seed data, createOrder, and API contract.
  3. Introduce a static exchange-rate table (or in-query constants) and rewrite the topCustomers sum to normalise amounts before aggregating.
  4. Add / update tests to cover overflow values and mixed-currency ranking.
  5. Document the exchange-rate update strategy for product (static constants, refreshed daily, or a rates microservice).

---

Estimate impact

All three assumptions are blocked, meaning none of the planned feature work can start safely on the current schema. The landmines are not cosmetic: two require schema changes (column type + new column) and one requires a query rewrite with a new exchange-rate dependency. A feature that might have been scoped as pure new work is now preceded by mandatory remediation on the data model. Expect the fix phase to add meaningful scope before the first line of multi-currency feature code is written. The exchange-rate strategy (static vs. live) is the largest remaining unknown and will drive the biggest variance in total effort.
